## 面试开场 3 分钟说法

这个项目一开始是一个开源的 Unity 2D 平台跑酷游戏。我选择它作为作品集基础，是因为它不是空项目，有比较完整的角色、地形、金币、UI、音频和游戏流程，更接近真实项目中“接手已有代码再开发”的情况。

我做的第一步是把项目 Fork 到自己的 GitHub 仓库，然后 Clone 到本地，并用 Unity 6000.2.6f2 跑通。跑通之后，我没有马上乱加功能，而是先阅读核心脚本：`RedCharacter` 负责角色移动、跳跃、死亡；`GameManager` 负责游戏状态、分数、重置；`Coin` 负责金币收集；`TerrainGenerator` 负责跑酷地图生成；UI 脚本负责界面切换和文本刷新。

功能上，我先做了 Dash 冲刺，因为它能体现角色控制、输入检测、冷却、速度覆盖、粒子和音效反馈。之后我增加二段跳、Coyote Time 和 Jump Buffer，用来改善平台游戏的跳跃手感。再往后，我增加动态难度速度成长和 Speed Up 提示，让游戏越跑越快，同时让玩家能看到成长阶段。

系统上，我增加了金币、最高分、上一局分数和声音设置的 PlayerPrefs 本地保存，并做了暂停界面的清除存档按钮。UI 上，我补充了游戏内金币显示、开始页和结束页数据展示、成就提示和操作提示。工程上，我修复了金币收集对象池为空的空引用问题，又补充了对象池重新生成对象时的状态重置，避免复用金币保留隐藏或无碰撞状态。

最后我整理了 README 和 `Docs/architecture.md`，让项目不仅能运行，也能被别人理解和复盘。

### 3. 修复金币空引用

原问题：金币收集后调用对象池回收，但某些金币没有绑定对象池，导致 `NullReferenceException`。

解决方式：

- 如果对象池存在，就回收到对象池
- 如果对象池不存在，就延迟销毁金币对象

面试说法：

```text
我给金币回收逻辑加了兜底处理，避免对象池为空时直接空引用。这是我第一次在项目里定位并修复运行时问题。
```

### 9. 对象池复用状态优化

问题：对象池复用对象时，如果对象被回收前关闭了显示或碰撞，再取出时可能仍然不可见或不能碰撞。

解决方式：

- 给 `IPoolable` 增加 `OnSpawnFromPool()`
- `ObjectPool.SpawnFromPool()` 取出对象后调用它
- `Coin` 恢复显示、碰撞、动画、粒子状态
- `CoinRigidbody2D` 恢复第二碰撞体和刚体速度

面试说法：

```text
对象池不是只把对象 SetActive 这么简单，复用时必须处理旧状态残留。我给池对象增加了生成生命周期方法，保证金币每次从池里取出都是干净状态。
```

## 面试官可能问的问题

### Q1：你为什么选择二次开发开源项目，而不是从零做？

答：因为我想模拟真实工作中接手已有项目的场景。真实公司里很多时候不是从零开始，而是在已有代码里读结构、定位问题、改功能、补文档。这个项目可以展示我阅读和改造已有 Unity 项目的能力。

### Q2：你这个项目里最能体现客户端能力的是哪部分？

答：我觉得是 Dash、跳跃手感优化和对象池状态修复。Dash 体现角色控制、输入、冷却、特效、音效和 UI 的联动；Coyote Time 和 Jump Buffer 体现输入容错和手感；对象池状态修复体现对象生命周期和运行时稳定性。

### Q3：Dash 是怎么实现的？

答：Dash 在 `RedCharacter.cs` 中实现。检测左 Shift 输入后，先判断角色是否死亡、是否正在 Dash、冷却是否结束。然后根据角色朝向设置横向速度，播放粒子和音效，同时短暂拉伸角色。持续时间结束后恢复缩放并退出 Dash 状态。

### Q4：Coyote Time 和 Jump Buffer 有什么区别？

答：Coyote Time 是离开地面后仍允许短时间跳跃，解决玩家刚走出平台边缘就跳不起来的问题。Jump Buffer 是提前按跳，在落地后自动执行，解决快落地前按早了没响应的问题。它们都是平台游戏常见的输入容错机制。

### Q5：为什么要做对象池状态重置？

答：对象池复用对象时，对象可能保留上一次使用时的状态。比如金币被收集后会关闭 SpriteRenderer 和 Collider2D，如果重新生成时不恢复，就可能出现看不见或碰不到的金币。所以我增加了 `OnSpawnFromPool()`，在对象被取出时统一恢复状态。

### Q6：本地保存为什么用 PlayerPrefs？

答：这个项目保存的数据比较轻量，例如金币、最高分、上一局分数和声音开关，用 PlayerPrefs 成本低、实现简单，适合 Demo 阶段。如果以后扩展成复杂背包、关卡进度或账号系统，可以再改成 JSON、SQLite 或服务端存储。

### Q7：你遇到过哪些问题？

答：比较典型的是金币收集空引用、对象池复用状态残留、UI 位置遮挡、Unity 版本升级导致的导入警告、以及运行时生成 UI 需要处理不同界面显示时机。这些问题让我意识到客户端开发不只是写功能，还要关注状态、生命周期、显示层级和玩家体验。

### Q8：这个项目还有哪些不足？

答：目前还缺正式构建包、截图/GIF 演示、更多关卡节奏设计和更完整的新手引导。代码上也还有继续拆分角色控制脚本、整理 UI 创建逻辑的空间。后续我会优先做构建发布和演示材料，让项目更适合投递。
